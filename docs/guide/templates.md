# 选择、定制与添加模板

## 1. 目标与前置条件

本指南帮助模板维护者为新的文档需求选择扩展位置，编写符合现有格式的模板，并让助手能够选择和验证它。普通写作请求直接参照[使用指南](usage.md)，无需先修改模板。

开始前准备：

- 一项具体读者任务，以及现有模板无法满足的内容或结构要求。
- 可编辑的技能包源码，包含 `templates/`、`docs/design-spec.md`、`docs/modules/` 和 `examples/`。
- 一份用于试写的真实材料，或明确标注用途的构造材料。
- 要运行包测试时，准备 Python 3.9 或更高版本和 `tests/` 目录。

下文路径均相对于技能包根目录。模板文件规定写法，生成文档仍保存到使用者指定的项目位置。

## 2. 选择扩展层级

先查[类型索引](../../templates/_index.md)，再决定修改现有类型、添加变体，还是补充一个模块。

| 需求差异 | 扩展位置 | 示例 |
|---|---|---|
| 只需调整本次文档的材料、深度或非固定顺序 | 本次写作请求 | 要求现有架构说明增加数据流解释 |
| 文档职责相同，但适用场景或展开结构不同 | 现有类型中的变体 | 在已有操作指南中定义特定场景的任务结构 |
| 文档职责和主体结构相同，只增加条件性内容 | 对应变体的可插模块 | 为操作指南增加数据准备模块 |
| 读者任务及必需回答的问题无法归入现有类型 | 新的类型文件 | 经比较后，确实需要独立的文档身份与验证标准 |

遵循**类型 → 变体 → 模块**的选择顺序。类型回答文档用来做什么；变体回答如何展开；模块回答当前场景还需要补充什么。

### 2.1 保留固定要求，定制其他内容

定制前，逐项辨认模板中的固定部分：

| 内容 | 定制规则 |
|---|---|
| 锚定节 | 保留其必须回答的问题；它们定义文档身份 |
| 必需字段 | 保留名称与字段要求，例如参数的类型、默认值和必填状态 |
| 明确固定格式 | 按原格式填写，例如步骤的结果确认、契约表字段 |
| 非固定顺序与表达 | 按读者任务调整，使用条目、表格、短段或图表达真实关系 |
| 可插模块 | 按适用条件选用，也可以定义新的模块 |
| 内容深度 | 按理解和执行需要展开，不由示例长度决定 |

先检查变体自己的限制。例如，PRD 的 Brief 变体不插入模块；需要额外模块时应使用 Lean，而不是直接扩写 Brief。

## 3. 添加变体或模块

### 3.1 添加变体

1. **打开现有类型文件。** 阅读它的定义、变体选择和类型验证标准，确认新变体仍服务于同一文档职责。
2. **增加选择条件。** 在 `## 变体选择` 中说明什么场景选新变体，并与已有变体区分。每个类型提供 2–5 种变体；若已达到上限，先合并重叠场景或重新判断类型边界。
3. **定义新变体的结构。** 写出锚定节、锚问、排版、可插模块和必要格式。锚问就是该节必须回答的具体问题。
4. **补充适用验证。** 在类型验证标准中标明新变体的专用要求及不适用项。比如仅与版本发布有关的检查，不应套到普通 PR Note。
5. **更新索引。** 修改 `templates/_index.md` 中的变体数量；默认变体改变时，同时修改 frontmatter 的 `default_variant` 和索引默认项。
6. **试写一份文档。** 用符合新变体选择条件的材料调用 skill，确认它选择新变体并保留对应锚定节。

### 3.2 添加可插模块

在目标变体的 `### 可插模块` 表中添加一行，填写全部五个字段：

| 字段 | 填写内容 |
|---|---|
| 模块名 | 能准确预期内容的名称 |
| 锚问 | 模块回答的具体问题 |
| 排版 | 步骤、定义列表、契约表、短段论证等表达形式 |
| 格式规范 | 必需字段、顺序或其他结构要求 |
| 有效性检验 | 什么内容有效，什么情况下属于填充 |

下面是用于操作指南的构造示意，只展示模块定义方式：

```markdown
| 数据准备 | 执行任务前要准备哪些数据？ | 定义列表 | 数据名称 / 获取位置 / 格式要求 / 检查方式 | 每项对应后续步骤实际使用的数据；与任务无关的条目删除 |
```

添加后，检查模块是否确实支撑后续任务。若内容相关但信息不完整，保留已知部分并说明需补充什么；若只是凑结构或与范围无关，则移除。模块的有效性规则按这一顺序使用。

## 4. 添加新的文档类型

### 4.1 创建文件并设置元数据

1. **选择类型标识。** 沿用现有小写英文及连字符命名，例如 `api-doc`。创建 `templates/{type}.md`，使文件名与 `type` 一致。
2. **填写文件开头的 YAML frontmatter。** 这是一段以 `---` 包围的元数据，用于说明类型、分类和默认变体。

| 键名 | 类型 | 必填 | 默认值 | 说明与约束 |
|---|---|---|---|---|
| `type` | 字符串 | 是 | 无 | 类型标识，与文件名对应 |
| `category` | 枚举字符串 | 是 | 无 | `engineering` 或 `knowledge-transfer` |
| `default_variant` | 字符串 | 是 | 无 | 默认变体标识，应与模板中的默认选择一致 |

以现有 `how-to.md` 为例，`type` 为 `how-to`，`default_variant` 为 `task-recipe`；正文用“变体 A: 任务食谱”作为显示标题，并在选择说明中指定它为默认变体。英文标识与中文标题通过这段说明对应，不要求把中文标题改成英文标识。新模板也应明确写出默认标识对应哪个变体。

### 4.2 填写模板结构

按[模板文件规范](../modules/5.2-document-templates.md) §5.2.8 编写。下面是结构示意，尖括号内容需要替换为实际定义；它展示文件组织，不是已登记的新类型。

````markdown
---
type: <类型标识>
category: knowledge-transfer
default_variant: <默认变体标识>
---

# <类型名称>
> <一句话定义读者任务与产物职责>

示例来源与用途见[来源登记](../examples/SOURCES.md)。

## 变体选择
- <条件 A> → <变体 A>（默认）
- <条件 B> → <变体 B>

## 变体 A: <名称>

### 锚定节
| 锚定节 | 锚问 | 排版 |
|---|---|---|
| <必需章节> | <必须回答的问题> | <表达形式> |

### 可插模块
| 模块名 | 锚问 | 排版 | 格式规范 | 有效性检验 |
|---|---|---|---|---|
| <模块> | <具体问题> | <表达形式> | <必需字段> | <有效条件与填充判据> |

### 示例
<按实际需要放入样本，说明范围、来源、内容性质和用途。>

## 变体 B: <名称>

### 锚定节
| 锚定节 | 锚问 | 排版 |
|---|---|---|
| <必需章节> | <必须回答的问题> | <表达形式> |

### 可插模块
<列出模块表；不提供模块时明确写“无”。>

### 示例
<按与变体 A 的关键行为差异选择必要样本。>

## 类型验证标准（Phase 4 Step 1c）
| 检查项 | 通过标准 | 不通过时处理 |
|---|---|---|
| <本类型的关键要求> | <可观察、可判断的条件> | <具体修正方式> |

## 权威参考
| 来源 | 类型 | 用途 |
|---|---|---|
| <原始资料及链接> | <教写法 / 成品逻辑 / 字段模板> | <采纳的写法或结构> |
````

选样本时按关键行为差异取样，不必为每个变体重复放同样的正文。需要特有排列、编号或字段规则时，在对应变体增加 `### 格式规范`。

### 4.3 编写类型专用验证

将该类型的关键任务转为可判断的条件，而不只重复“表达清晰、内容完整”。例如，操作类文档可检查“每个关键动作是否有对应结果确认”；参数类文档可检查“每个公开参数是否给出类型、默认值和必填状态”。

按所属类别组织：

- **工程文档**：沿用检查项、判定标准及修正方式的表格。
- **知识传递文档**：除结构检查外，增加类型边界检查；需要时补充可查阅性或可理解性等质量检查。
- **变体专用要求**：写明适用变体，避免把某一变体的字段误当作所有变体的必填项。

通用表达和真实性规则继续引用主规格。确有独立领域要求时，先检查 `docs/design-spec.md` §3.4 的已有编号，再使用尚未占用的 D 系列编号，并由模板明确引用；D1 已用于架构文档质量清单。

### 4.4 登记类型并同步说明

1. **在 `templates/_index.md` 添加索引行。** 放入工程生命周期或知识传递分组，填写类型名称、相对文件链接、默认变体和变体数。
2. **核对公开的类型清单。** 同步根 `README.md`、`SKILL.md` 描述和 `docs/design-spec.md` §5.2 中的类型枚举或数量；更新 `docs/modules/5.2-document-templates.md` §5.2.5 的类型与变体总览。入口工作流和扫描器不需要因新增类型而重写。
3. **同步安装副本。** 将新增模板及修改的索引、规则或来源记录更新到实际调用的包中。源码与安装目录分开时，编辑源码不会自动改变安装内容。

确认：索引链接能打开模板，默认选择与 frontmatter 一致，实际加载的包内也有相同文件。

## 5. 处理示例、来源与注释

### 5.1 登记示例用途

模板示例分为真实来源片段、源码改编和构造示意，按用途标明：

| 示例性质 | 模板旁说明 | 来源登记内容 |
|---|---|---|
| 真实来源摘录或翻译 | 来源、版本、片段范围、翻译或改编性质 | 在 `examples/SOURCES.md` 登记固定位置、适用许可、署名、修改范围及核验状态 |
| 项目源码改编 | 对应代码版本、示范的结构和省略范围 | 登记实现依据与用途，区分实现描述和实际运行记录 |
| 构造示意 | 明确说明只教语法、排版或结构 | 说明构造性质和使用范围，不写成真实业务数据 |

在 `examples/SOURCES.md` 中为每段样本登记以下内容：

- **来源与位置**：标题、作者或组织、固定链接、章节或行范围、版本或获取日期。
- **再分发依据**：实际适用的许可文本、范围、署名和使用条件。
- **内容性质**：摘录、翻译或改编，以及修改和省略了什么。
- **适用与验证**：对应类型和变体、示范的写法、已核对的技术版本及核验范围。
- **状态**：待核验或已核验；来源、许可和内容核对完成后，再作为正向写法样本使用。

第三方示例按其许可保留版权、许可证和所需 NOTICE，并放入 `examples/licenses/`。现有记录格式见[来源记录](../../examples/SOURCES.md)。

### 5.2 写清注释的作用

注释用于说明示例中的非直观条件、必须保留的结构或具体改编范围。把影响使用者决策的前提直接写在正文中，不藏进 HTML 注释。

- 代码注释使用该语言允许的语法；JSON 的说明放在代码块外。
- 保留引用代码中的原始注释，改写或翻译时说明范围。
- 模板中的操作示例附必要前提和结果确认，使读者能判断完成条件。
- 扫描豁免注释只用于有具体理由的原文保留，不能替代类型验证和事实核对。

## 6. 验证扩展结果

1. **检查静态结构。** 确认类型文件、frontmatter、索引、变体数、锚定节、模块字段及本地链接对应一致。
2. **更新相关包测试。** 新增类型时，同步 `tests/test_package_contract.py` 的 `TYPES` 预期集合，并检查 `test_template_index_and_metadata` 中的元数据及来源状态断言是否适用。修改受保护示例时，在 `tests/test_example_sources.py` 中同步对应内容校验；先核验实际改动，再更新预期值。
3. **在技能包根运行自动测试。**

   ```bash
   python3 -B -m unittest discover -s tests -v
   ```

   确认：结果为 `OK`；若失败，按失败项修正对应文件或契约。包链接测试会遍历 `docs/` 中的 Markdown，没有忽略本地试写稿的开关。开发目录混有试写材料时，将待交付包文件连同 `tests/` 复制到一个新测试目录，在该目录运行同一命令；保留原工作区文件。

4. **在已更新的安装包上试写。** 用一份真实材料触发新类型或变体，检查选择是否正确、必需章节是否齐全、类型验证是否执行。再用一份缺少必要信息的材料，确认模型保留已知事实并指出需补充的内容。
5. **扫描试写产物并检查阅读效果。** 让助手按正常流程裁决候选；重要文档再检查未参与写作的读者能否完成操作、查询或理解任务。

完成后，沿[使用指南](usage.md)中的调用方式使用该模板。扩展成功的判断是读者任务得到正确结构和对应验证，而不只是索引中多了一行。
