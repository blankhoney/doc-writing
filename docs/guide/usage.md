# 使用指南

本指南说明如何用 doc-writing 新建文档、修改已有内容，以及检查一份已保存的 Markdown。首次使用可先完成[快速上手](README.md)；这里按任务组织调用方式，不展开内部架构。

## 1. 前置条件

- 在目标项目的会话中使用已安装的 `doc-writing`，通过 `/skills` 确认入口可见。
- 将材料放在助手可读取的位置，或直接贴在请求中。涉及当前实现时，保持会话位于对应项目。
- 需要保存或修改文件时，明确目标路径及允许修改的范围，并具备相应写入权限。

文档类型、模板变体和内建检查由助手根据任务选择。只需说明要写什么；已有固定章节、读者、篇幅或输出要求时，再补充这些条件。

## 2. 根据材料新建文档

### 2.1 提交写作请求

1. **提供材料和目标。** 可以引用一个文件，也可以直接给出任务所需事实。下面是完整的调用示意，可直接用于生成一份示例操作指南：

   ```text
   /doc-writing 根据以下材料，写一份给团队成员的报销申请指南，只在对话中输出：申请人在每月 25 日前提交当月发票和费用说明；直属负责人审核；财务复核后安排付款。
   ```

2. **补充影响正文的关键缺口。** 当材料不足以确定实际操作、范围或交付方式时，回答助手集中提出的问题。已经明确的条件会直接用于编写。

3. **查看目标产物。** 上述示例应得到一份围绕提交、审核和付款安排的操作指南；指南说明材料中已有的期限与申请材料。真实使用时，将示例材料换成团队的实际规定。

### 2.2 引用项目文件并保存

已有材料在项目内时，直接写出路径。以下调用形式示意假设 `docs/requirements.md` 已存在：

```text
/doc-writing 根据 docs/requirements.md，为新加入项目的工程师编写功能说明，保存到 docs/feature-guide.md。
```

保存前，助手会读取已有目标文件并保留任务外内容。完成后，打开 `docs/feature-guide.md`，确认得到所需说明。文件名由交付用途决定，不需要与模板文件同名。

## 3. 按任务指定产物

下面的类型标识可以写在 `/doc-writing` 后，也可以只用中文描述目标。表中的请求片段用于说明选题；引用文件或日志时，替换为当前项目真实材料。

| 你要完成的任务 | 类型标识 | 请求片段示意 |
|---|---|---|
| 明确功能目标与验收条件 | `prd` | 根据已确认需求写产品需求文档 |
| 提出技术方案与取舍 | `tech-design` | 根据接口约束设计接入方案，说明选择与代价 |
| 描述鉴权、端点和错误响应 | `api-doc` | 根据当前路由及接口定义写 API 文档 |
| 向使用者说明版本影响 | `changelog` | 根据指定版本的变更记录写发布说明 |
| 汇报运行结果或制定测试安排 | `test-report` | 根据本次流水线日志写 CI 报告 |
| 编写部署或值班操作 | `deploy-runbook` | 根据部署配置写操作手册 |
| 记录一项已作出的决策 | `adr` | 根据会议记录整理决策、依据与后果 |
| 引导新手学会一个任务 | `tutorial` | 写一份从准备环境到首次完成导出的教程 |
| 帮已有基础的人完成操作 | `how-to` | 根据操作材料写报表导出指南 |
| 提供参数或接口查询 | `reference` | 根据配置定义写参数参考 |
| 解释当前项目的组成与机制 | `explanation` | 根据项目实现说明架构及组件职责 |

完整变体见[模板索引](../../templates/_index.md)。不知道类型时，直接描述读者要完成的任务，助手会匹配模板。

### 3.1 补充有用的上下文

按当前任务需要补充信息，不必每次填写所有字段：

| 信息 | 何时提供 | 示例 |
|---|---|---|
| 目标读者 | 阅读基础影响解释深度 | 熟悉 Python，但第一次接触本项目 |
| 依据版本 | 当前实现、历史行为和目标设计不同 | 以当前分支代码为准；或以指定发布版本为准 |
| 资料路径 | 事实在文件中，不能只靠请求确定 | `docs/requirements.md`、接口定义、运行日志 |
| 固定内容 | 必须沿用团队或客户格式 | 保留现有的输入、输出、验收三节 |
| 修改范围 | 只允许改部分已有内容 | 只修改安装和配置章节 |
| 输出方式 | 要预览、保存或更新原文件 | 只输出正文；或保存到 `docs/setup.md` |

运行结果类文档需要对应日志或记录；需求和方案类文档则应提供目标、约束与已确认选择。材料不同，产物的事实依据也不同。

### 3.2 调整深度和组织方式

用读者任务描述深度，比逐条指定内部规则更直接。例如：

```text
/doc-writing 根据已有需求，写一份供跨团队评审的方案说明，展开组件职责、交互、备选方案和迁移安排，保存到 docs/proposal.md。
```

如果只需短文，可以要求 Brief、备忘或简短说明。助手仍按所选模板保留必需内容；当任务需要更多条件、论证或步骤时，会据此展开，而不是机械压缩到固定字数。

## 4. 修改已有文档

### 4.1 调整内容和表达

1. **指定原文、依据与允许改动的部分。** 以下调用示意假设文件已存在：

   ```text
   /doc-writing 对照当前项目配置，更新 docs/setup.md 的安装和配置章节，保留其他章节，直接修改原文件。
   ```

2. **说明需要保留的作者内容。** 有固定术语、原始引文或必须保留的观点时，在请求中指明。助手会保留有效经验与立场，并依据材料纠正事实。

3. **查看修改后的目标章节。** 确认步骤和配置符合当前项目、任务外章节保持原样。需要进一步调整时，给出具体阅读障碍，例如“默认配置在哪里仍不清楚”，而不只是“再优化一下”。

### 4.2 只检查，暂不改写

先诊断再决定修改时，明确限制：

```text
/doc-writing 检查 docs/architecture.md 的结构、术语和实现描述，列出具体位置及修改建议，不修改文件。
```

预期得到问题位置与建议，而不是被直接替换的正文。决定采纳后，再指定需要执行的修改。

### 4.3 合并相关短文

让助手按阅读任务判断合并，而不是只按字数拼接：

```text
/doc-writing 整理 docs/guide/ 中的文档，将同一阅读任务下内容较短且重复的页面合并，保留操作、参考和原理说明各自的用途。先给出文件调整建议，不修改文件。
```

查看建议中的阅读入口、合并关系和链接调整，再授权执行。文件数量应服务于查找和独立使用：短小的参数说明可以并入相应参考页，完整操作指南则保留自己的前提和步骤。

## 5. 单独扫描已保存文档

需要独立定位用词和格式候选时，可以直接调用随包脚本。该操作需要 Python 3.9 或更高版本，只使用标准库。

1. **定位脚本与目标文件。** 以下示例假设终端位于目标项目根目录，skill 安装在项目级目录，并已有 `docs/guide.md`：

   ```bash
   python3 .claude/skills/doc-writing/runtime/doc-lint.py -- docs/guide.md
   ```

   确认：末尾统计显示完成文件数量和错误数量。退出码 `0` 表示扫描完成；`2` 表示参数、输入或规则读取发生错误。

2. **按行号查看候选原文。** 输出中的 `文件:行号:warning/类别:命中文本` 指向需要复查的位置。根据原文的含义、引用和具体条件决定修改或保留；脚本本身不改写文档。

3. **根据项目格式选择扫描项。** 例如，项目采用自己的中英文间距规则时，可以关闭间距候选：

   ```bash
   python3 .claude/skills/doc-writing/runtime/doc-lint.py --skip-format spacing -- docs/guide.md
   ```

   确认：该次输出不再包含 `spacing` 候选，其他扫描类别继续执行。

从其他目录调用时使用实际脚本绝对路径；文档路径相对于终端当前目录解析。其他格式选项与局部豁免见[扫描器参考](../../README.md#候选扫描器)。

## 6. 常见问题

| 遇到的情况 | 处理方式 |
|---|---|
| `/skills` 中找不到入口 | 检查安装目录是否包含 `SKILL.md` 及完整资源包；重新打开项目会话后再检查。安装位置见[项目 README](../../README.md#安装)。 |
| 材料不足，助手需要补充信息 | 提供影响正文的事实或明确保留为待确认；没有运行记录时，不要求把预期结果写成实测结论。 |
| 希望先预览，不覆盖已有文件 | 在请求中写明“只在对话中输出”或“不修改文件”；审阅后再指定允许保存的路径和范围。 |
| 候选扫描未执行 | 根据交付说明检查 Python、脚本路径或执行权限。扫描未执行不等于没有问题，也不阻止先取得正文和模型检查结果。 |
