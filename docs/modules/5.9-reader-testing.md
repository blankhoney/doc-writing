### 5.9 读者测试与阅读体验验证

**问题**：作者可能把已有上下文当作读者常识。主检负责形式与语义；独立读者测试检查无写作上下文时的理解和使用障碍。

**参考与改进**：doc-coauthoring skill 的 Stage 3 提出了"用无上下文 subagent 模拟读者"的方法。我们在此基础上做三个改进：

1. **错误分类**：不只检测"回答对不对"，而是区分误解、费解、缺失、错误推断四种问题类型
2. **多角色读者**：不同读者有不同知识背景，同一文档对不同角色可能产生不同理解
3. **约束回溯**：每个阅读问题回溯到违反了哪条约束，形成修正 → 重测闭环

#### 5.9.1 读者测试流程

```
文档通过收尾检查（3.5）
    ↓
Step 1: 主 agent 预测读者问题（5-10 个）
    ↓
Step 2: 启动读者 subagent（无上下文 fresh agent）
    ├─ 输入：仅文档全文 + 测试问题
    ├─ 不给：写作过程的上下文、需求背景、决策讨论
    └─ 角色：指定读者画像（见 5.9.2）
    ↓
Step 3: 读者 subagent 回答问题 + 主动报告理解障碍
    ↓
Step 4: 主 agent 对比预期答案，分类问题（见 5.9.3）
    ↓
Step 5: 问题回溯到约束违反（见 5.9.4）→ 修正 → 重测
    ↓
退出条件：读者 subagent 对所有问题回答正确，且未报告新的理解障碍
```

#### 5.9.2 读者角色设计

不同文档类型需要不同的读者角色。读者 subagent 的 prompt 中指定角色背景，影响其"已知知识"。

**技术架构决策文档的读者角色**：

| 角色 | 已知知识 | 测试重点 |
|------|---------|---------|
| 团队新成员 | 通用技术能力，不了解本项目历史和现有系统 | 术语是否定义清楚、上下文是否充分、隐含假设是否显式 |
| 相邻团队技术负责人 | 了解公司技术栈，不了解本团队的业务细节 | 系统边界是否清晰、接口约定是否明确、依赖关系是否说清 |
| 技术评审委员会 | 广泛技术经验，关注风险和取舍 | 决策理由是否充分、取舍是否显式、风险是否被识别 |

**选择规则**：

- 至少用一个"低上下文"角色（新成员）测试，检查项目知识缺口
- 关键决策文档额外用一个"高挑战"角色（评审委员会）测试——检验论证强度
- 不需要每次都测所有角色。默认测新成员，主 agent 判断文档重要性后决定是否增加角色

#### 5.9.3 问题分类体系

读者 subagent 的回答问题按以下四类分类，每类对应不同的修正策略：

| 问题类型 | 定义 | 识别信号 | 修正方向 |
|---------|------|---------|---------|
| **误解** | 读者理解了但理解错了 | 回答自信但与预期答案矛盾 | 产生歧义的表述需要重写，通常是术语未定义（C6）或事实/假设未区分（G2） |
| **费解** | 读者无法形成理解 | 回答含糊、承认不确定、要求更多信息 | 缺少前置知识说明或逻辑跳跃过大，通常是结论先行不足（C1c）或上下文缺失 |
| **缺失** | 文档未覆盖读者需要知道的信息 | 读者提出了文档未回答的合理问题 | 范围内的缺失需要补充内容；范围外的缺失说明范围声明可能不准确（C5） |
| **错误推断** | 读者基于文档信息推导出错误结论 | 读者的推理链条合理但结论错误 | 最危险的问题——文档的隐含逻辑引导了错误推理，需要增加显式约束或澄清 |

#### 5.9.4 约束回溯机制

每个读者测试发现的问题回溯到约束体系，判断是哪条约束执行不到位导致了问题：

| 问题类型 | 常见对应约束 | 回溯检查 |
|---------|------------|---------|
| 误解 | C6 一物一名 | 误解的概念是否有唯一定义？ |
| 误解 | G2 认知状态 | 读者是否把假设当成了事实？ |
| 费解 | C1c 结论先行 | 读者需要的结论是否在段落开头？ |
| 费解 | C2 具体化 | 描述是否足够具体让读者建立心智模型？ |
| 缺失 | C5 范围锁定 | 缺失信息是否在声明范围内？ |
| 缺失 | D1 质量清单 | 架构文档必答问题是否都回答了？ |
| 错误推断 | C3 判断义务 | 是否因为没有显式下判断，读者自己推导了一个错误的？ |
| 错误推断 | G2 认知状态 | 是否因为事实和假设混写，读者基于假设做了确定性推理？ |

**修正 → 重测循环**：

```
发现问题 → 回溯到约束 → 修正对应段落 → 仅重测修正段落相关的问题
    ↓
重测通过 → 下一个问题
重测仍失败 → 主 agent 人工分析根因（可能不是约束问题而是内容问题）
```

**循环上限**：同一段落修正 3 次后仍有读者测试问题，标记为需要人类审阅，不再自动修正。避免无限循环。

#### 5.9.5 读者 subagent 的 prompt 模板

```markdown
你是一个技术文档的读者。你的角色是 [角色名]。

你的背景：
[角色的已知知识描述]

你不知道：
- 这份文档是如何写出来的
- 写作过程中讨论了什么
- 任何文档中没有明确写出的信息

请完成以下任务：

1. 阅读文档全文
2. 回答以下问题（每个问题独立回答，基于文档内容）：
   [问题列表]
3. 对每个回答标注你的确信度：确定 / 大致确定 / 不确定 / 无法判断
4. 主动报告：
   - 你在阅读中遇到的理解障碍（哪里停下来想了很久）
   - 你认为文档假设你已经知道但实际没有说明的知识
   - 你发现的内部矛盾或不一致
   - 你基于文档推导出的结论中，你不确定作者是否同意的部分
```

#### 5.9.6 读者测试与收尾检查的关系

读者测试在收尾检查之后执行。两者的区别：

| 维度 | 收尾检查（3.5） | 读者测试（5.9） |
|------|---------------|----------------|
| 检查对象 | 写作规范与语义 | 无写作上下文时的理解与使用 |
| 执行者 | 主 agent 自检 | 无上下文 subagent |
| 检查方式 | 按完整规则判断内容与表达 | 模拟阅读 + 回答问题 |
| 发现类型 | 形式、事实、论证、可操作性等 | 误解、费解、缺失、错误推断 |
| 执行时机 | 每次输出前 | 关键文档完成后 |
| 执行成本 | 低（主 agent 内部） | 高（启动 subagent） |

**触发条件**：不是所有文档都需要读者测试。触发条件：

- 架构决策文档、技术方案设计等需要多人评审的文档 → 必须测试
- 变更说明、API 文档等参考性文档 → 可选
- 内部笔记、草稿 → 不需要
