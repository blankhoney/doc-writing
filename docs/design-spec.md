# 文档写作 Skill 设计规格

当前运行依据为本规格及模块。

## 1. 目标

构建一个 Claude Code skill，约束 AI 在代码工程全流程中生成符合专业标准的技术文档。解决的核心问题：AI 生成的文档存在填充、模糊、逃避判断、抽象空洞、范围蔓延、术语混乱六类系统性缺陷。

本文档记录约束体系、技术选型依据和模块设计。首版入口为包根的 `SKILL.md`，运行时位于 `runtime/`；模型读取完整规则并主检，小脚本仅提供候选。完整包由用户手动调用，不使用 hook；正式开源发布前仍需完成示例来源、许可和实际调用验收。

## 2. 问题根因分析

从同事总结的 70+ 条写作问题中归纳六类表现。以下模型成因是设计假设，未做因果实测。

### 2.1 填充冲动

**表现**：开场铺垫、段末重复总结、"首先/其次/最后"强行拆分、同一意思换说法重复、每章用相同模板、机械凑出三条收益三条风险、20% 的内容膨胀至 5 倍篇幅。

**根因**：模型后训练偏向"有帮助感"，用冗余文本填充输出长度。对称结构（每段差不多长、每个方案列同样多的条目）被模型当作"完整性"的信号。

**覆盖的原始规则数**：约 18 条。

### 2.2 模糊回避

**表现**：用"部分、相关、一定程度上"代替具体对象，"高可用、高性能"代替量化目标，堆砌修饰词（显著、深入、全面、充分），"进行了优化"代替"优化了"。

**根因**：模型回避明确判断以降低输出错误率。模糊表达是一种安全策略——说得越笼统越不容易被证伪。

**覆盖的原始规则数**：约 15 条。

### 2.3 判断逃避

**表现**：列完优缺点不给结论，"需要结合实际情况综合判断"收场，"后续持续优化"处理所有未解决问题，备选方案凑数或故意写弱，十几页后读者仍不知道最终决定。

**根因**：模型把"不下判断"当作客观中立，实际上是把决策成本转嫁给读者。

**覆盖的原始规则数**：约 14 条。

### 2.4 抽象成瘾

**表现**：赋能/协同/闭环/抓手/范式等大词，组件叫"智能决策中心""统一能力平台"但说不清职责，架构原则无法排除任何方案，"本质上、底层逻辑"后面没有新信息。

**根因**：抽象词汇在训练数据中高频出现，模型把它们当作专业性信号。抽象程度越高，适用范围越广，模型越倾向使用。

**覆盖的原始规则数**：约 12 条。

### 2.5 范围蔓延

**表现**：先写行业趋势再切正题，技术百科式铺陈，为未来需求过度设计，动辄"统一、全局、平台化"但未论证必要性。

**根因**：模型缺少范围边界意识，任何相关内容都倾向纳入输出。

**覆盖的原始规则数**：约 8 条。

### 2.6 术语混乱

**表现**：同一事物在同一文档中出现全称、缩写、英文、中文翻译四个名字。术语未定义就使用。术语在不同段落含义漂移。

**根因**：模型在训练中见过同一概念的多种表达，生成时随机采样不同变体。

**覆盖的原始规则数**：约 5 条。

## 3. 约束体系设计

### 3.1 设计原则

按四层组织规则。仅保留高层原则可能遗漏适用条件，这是保留完整规则的设计假设，效果待实测。

| 层级 | 作用 | 执行方式 |
|------|------|---------|
| 核心约束 | 通用写作要求 | 模型理解并执行 |
| 边界护栏 | 具体条件与优先级 | 模型按上下文裁决 |
| 领域子规则 | 类型专用要求 | 按所选变体执行 |
| 收尾检查 | 核对全文 | 模型主检含语义判断，脚本补充候选 |

### 3.2 核心约束（6 条）

> 原文：[共同约束](modules/constraints-common.md)。

### 3.3 边界护栏（3 条）

这三条约束解决的问题是：模型在执行核心约束时产生的已知逃逸模式。它们不是新方向，而是对核心约束的加固。

> 规则原文：G1/G3 见[编写规则](modules/constraints-writing.md)，G2 见[共同约束](modules/constraints-common.md)。首次生成文稿前补齐 G1/G3，真实性与范围边界先于取材。

### 3.4 领域子规则

> 原文：[技术架构决策约束 D1](modules/constraints-architecture.md)。实际提出相应方案前完整读取；模板保留其类型层检查与变体适用条件。

### 3.5 收尾检查清单（原始规格，运行时已合并）

> 原 11 项责任与完整原文均见[检查入口](../runtime/verify-checks.md#35-收尾检查清单原始规格运行时已合并)。不重复执行同义检查，也不取消任何适用责任。

### 3.6 端到端工作流

约束体系（3.2-3.5）管"写作规则"，模块设计（§5）管"各环节怎么做"。本节将它们串联为完整流程，明确每个阶段的输入、输出和执行顺序。

```
Phase 1 准备 → Phase 2 信息获取 → Phase 3 编写 → Phase 4 验证管线 → Phase 5 交付
                                      ↑                    |
                                      └── 修正循环 ─────────┘
```

> 阶段原文：完整动作按阶段移至[准备](../runtime/prepare.md)、[取材](../runtime/research.md)、[编写](../runtime/write-assist.md)、[验证与交付](../runtime/verify-checks.md)。任务提前产生文稿时，对应写作前置同步提前；已完整读取且仍可用的规则无需每阶段重复读取。

## 4. 技术选型依据

约束体系的设计参考了以下标准和实践，按实际采纳程度排列：

### 4.1 直接采纳

| 来源 | 采纳内容 | 用于 |
|------|---------|------|
| ASD-STE100 | 一词一义原则、句长约束思想、强制主动语态 | C6 一物一名、G1 禁用句式 |
| i-have-adhd skill | 首行规则、禁止清单、发前检查机制 | G1 禁用清单、收尾检查流程 |
| RFC 2119 | MUST/SHOULD/MAY 语义分级 | C3 判断义务中的约束强度标记 |
| Google Tech Writing | 范围+非范围声明、读者定义、关键信息前置 | C5 范围锁定 |
| Ponytail skill | 删除优于添加、范围纪律 | C1 信息密度、C1a 反对称 |
| Diátaxis 框架 | Tutorial / How-to / Reference / Explanation 四类及其边界 | 5.2 类型与模板 |

### 4.2 参考但未直接采纳

| 来源 | 参考内容 | 未采纳原因 |
|------|---------|-----------|
| ASD-STE100 受控词汇表 | 限定可用词汇的完整清单 | 航空领域专用，技术文档场景不适用 |
| ASD-STE100 句长硬限制 (20/25 词) | 指令句 ≤ 20 词，描述句 ≤ 25 词 | 中文句法结构不同，硬性字数限制不合理，保留"尽量直接"的软约束 |
| Plain Language Guidelines | 日常词汇、直接称呼读者 | 部分融入 G1 禁用清单，未作为独立约束 |
| Vale linting | 自动散文检查 | 首版不引入外部 lint 集成；采用本地小脚本候选定位，不使用 hook |

## 5. 模块设计

以下模块支撑端到端工作流（3.6）的各阶段。

### 5.1 渐进式披露
保留 H1–H9 行动提示、分阶段读取和类型层结构，但不以压缩预算代替完整约束。模型读取全部适用规则并主检，脚本只补充字面和格式候选；实际效果需要真实任务验证。

| 层级 | 内容 | 加载条件 |
|------|------|---------|
| L0-init | 手动入口、工作流与完整读取要求 | 用户调用 `/doc-writing` |
| 共同约束 | 完整 C1–C6、全部子规则与 G2 | 调用后先读，先于取材与范围决定 |
| 阶段原文 | prepare：Phase 1 与选型；research：Phase 2 与 5.6 | 准备与选型前；核对或获取材料前 |
| L0-write | 完整 G1/G3、Phase 3、5.2.2 与常规表达规范 | 首次文稿、实际骨架文字或建议前，提前输出则提前读 |
| 架构约束 | 完整 D1 | 实际提出技术架构决策前，包括详细设计中的架构选择 |
| L0-check | 原 11 项收尾、Phase 4/5 与完整 5.3 | 初稿后、交付前，重新核对全部适用规则 |
| L1 类型层 | 完整当前模板、变体与类型验证 | 确定类型后、骨架形成前 |
| L2 条件资源 | 类型比较、额外示例、图表代码、设计分支、测试证据与读者测试 | 相应动作前按条件 Read，不批量加载 |
| Script | G1 字面与格式候选 | Phase 4 直接调用，输出由模型裁决 |

Python、脚本或权限不可用时由模型完整检查并说明限制，不删规则、不宣称脚本通过。备忘/Brief 快速路径保留必要证据核验，不增加规则 ID 或复杂调度。

> 详述：[modules/5.1-progressive-disclosure.md](modules/5.1-progressive-disclosure.md)

### 5.2 文档类型模板与示例
三级选择架构：类型 → 变体 → 模块定制。沿用标准技术文档分工，保留所选模板的锚定节、必需字段和明确固定格式；读者需求可调整内容、深度、非固定顺序与表达、自定义模块，不锁死全文。

- **9 种排版类型**（倒金字塔、问题→方案→代价、有序步骤+验证信号、定义列表、契约表、时间线、差异对照、决策日志、索引+深链）作为跨文类一等公民
- **锚定节 + 模块槽位**：锚定节不可删（定义文档身份），模块按 5.2.3 的有效性规则处理：空洞或无关内容删除，相关但信息不完整时保留已知事实并标注缺口
- **2-5 变体/类型**：默认由风险/范围决策树选择（类型有特殊维度时以模板为准），默认走 Lean，合规变体仅当客户/法规要求
- **11 文档类型**：工程 7 类（PRD、技术设计、API、Changelog、测试报告、部署/Runbook、ADR）+ Diátaxis 4 类（Tutorial、How-to、Reference、Explanation）
- **示例**：按 5.2.7 区分短文、长文片段和构造示意，用途与状态见[来源清单](../examples/SOURCES.md)；取样长度不限制全文
- **参考源三级分类**：教写法 / 成品信息架构 / 字段模板，不混用

> 详述：[modules/5.2-document-templates.md](modules/5.2-document-templates.md)

### 5.3 验证管线详述
细化 Phase 4 各 Step 的检查逻辑：完整模型主检与脚本候选裁决（Step 1）、内容对齐（Step 2，按版本/时间点核对代码、配置及实际运行结果）、叙述重复度（Step 3，检查跨章节冗余，保留独立阅读单元所需的必要重复）、滑动检查（长文档逐节内嵌检查）、类型专用验证（Step 1c，从 L1 模板读取，Diátaxis 类型采用二至三层验证结构）。

> 详述：[modules/5.3-verification-pipeline.md](modules/5.3-verification-pipeline.md)

### 5.6 信息获取与上下文管理

> 完整路由、事实卡片格式和污染防护见[信息获取](../runtime/research.md#56-信息获取与上下文管理)。核对或获取材料前读取，不能因材料本地可用而忽略证据和授权边界。

### 5.7 Subagent 约束注入
**问题**：subagent 编写文档时默认不携带主 agent 的写作约束。

**原则**：编写环节尽量由主 agent 完成（见 Phase 3）。只在以下场景委托 subagent：

- Best-of-N 竞选中的候选章节生成
- 长文档中独立性高的章节（章节间无强依赖）
- 主 agent 上下文已满需要分段处理时

#### 约束注入方式

按 subagent 类型选择：

| 场景 | 注入方式 | 原理 |
|------|---------|------|
| fork subagent | 继承已读上下文 | fork 不清空主 agent 上下文；仍须补齐本任务尚未读到的阶段原文、完整模板与适用条件资源 |
| fresh subagent | 包内约束路径注入 | prompt 中给出包内 `SKILL.md` 与当前模板的绝对路径；先完整读共同约束、当前阶段及适用文类规则，写文稿前补齐编写规则；不另复制一份约束 |

#### 主 agent 审查（必选）

无论使用哪种注入方式，主 agent 必须对 subagent 产出执行收尾检查清单（3.5）。原因：约束注入解决的是"subagent 知道规则"，不能保证"subagent 遵守规则"。

```
subagent 产出候选文本
    ↓
主 agent 执行收尾检查清单（3.5）
    ↓
合格 → 采纳或选优合成
不合格 → 主 agent 修正或重写
```

主 agent 对最终候选文本执行完整检查，可直接调用候选脚本辅助定位（见 5.3.3）；不使用 hook。

### 5.8 结构化表达规范
按信息类型选择动作、条目、论证、图或文件树，说明调用关系与图文边界；沿用表格、标题、代码块和符号约定，附必要构造示意。

> 详述：[modules/5.8-structured-expression.md](modules/5.8-structured-expression.md)

### 5.9 读者测试与阅读体验验证
用无上下文 subagent 模拟读者，检测知识诅咒。四类问题分类（误解/费解/缺失/错误推断），每类对应不同修正策略。问题回溯到约束体系形成闭环。多角色读者（默认测新成员，关键文档加评审委员会）。同一段落修正 3 次仍有问题则标记人类审阅。

> 详述：[modules/5.9-reader-testing.md](modules/5.9-reader-testing.md)
