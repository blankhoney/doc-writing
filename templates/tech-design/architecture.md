# 架构方案指导

从[技术设计](../tech-design.md)进入，沿用所选变体锚定节；实际提出架构决策前读[完整 D1](../../docs/modules/constraints-architecture.md)，不等验证时才补读。本文补写法，不复制模板；备忘只在原节回答当前决策。

## 写到可评审

| 要回答的问题 | 具体表达 |
|---|---|
| 当前到目标改变什么 | 对齐 PRD、初版方案与证据版本，给目标边界、非目标及关键需求落点；新提议与既定决定分开 |
| 谁负责、谁依赖谁 | 结构图配职责，标出外部系统、数据／状态／控制权归属；按 [Mermaid 规范](../../docs/modules/5.8-mermaid.md)选择视图，不按服务架构套用文件或工具系统 |
| 关键场景如何完成和失败 | 给触发、参与者、交互顺序与可见结果；展开影响选择的失败、安全、性能、一致性及恢复条件 |
| 为什么选此方案 | 对比现实候选、约束和实施／回退成本，说明取舍；迁移与兼容按已有系统需要展开 |
| 如何开始实现与验证 | 标出依赖顺序、待决事项、质量场景和验证点；代码级内容转入详细设计，不另造实施追踪系统 |

信息缺失时保留已知部分、影响和补证方式。在确认目标内主动补职责与契约；不能从模板空项推导新产品要求。优先现有 API、SDK、普通函数与运行时保障。

## 减法与必要观测

按 D1 复杂度行核对新增环节；复审优先指出可删除、合并、移入已有日志或在原调用点修正的内容。

业务操作、观测、操作系统／运行时保障、测试／人工审阅分别说明。普通遥测失败独立记录，保留确证业务事实；结果未知时不报成功。明确的审计、安全或事务前置继续执行，局部动作成功不能覆盖其失败。不把测试取证接成生产放行链。

必要埋点回答具体问题，优先已有信号。需要展开时用“问题／事实源或采集点／字段与单位／使用及缺失处理”小表；按需保留关联标识、动作、结果、耗时、错误和清理状态，考虑敏感性、基数与保存成本。日志、网络信号、文件检查和资源结果各按自己的证据范围解释，不另建证明平台。

## 分支检查

在父模板全部适用检查之外，确认：

- 关键需求能定位到边界、职责、场景与验证；提案、事实和未决可区分。
- 图文名称、关系方向及状态一致；每张图回答声明的问题，按 [Mermaid 规范](../../docs/modules/5.8-mermaid.md)实际渲染或说明未验证。
- 正常与关键失败场景连贯，数据和控制权无含混归属；取舍有当前约束依据。
- 新增复杂度经 D1 四问核对；观测故障与业务／审计契约分清，必要保障未被减掉。
- 关键假设有验证办法，未决事项给决策条件，不编负责人、日期或运行结果。
