# 程序详细设计指导

从[技术设计](../tech-design.md)进入，保持原有变体锚定节；以下内容放入方案，代价和未决归原节。新项目可直接依据需求设计，路径和接口未存在时标为拟议。

先读[代码规范](code-conventions.md)，形成当前任务的代码约束。按 PRD、初版方案和选定代码版本核对关键需求，主动补实现缺口，不把新提议写成已批准或已实现。

## 展开实现所需内容

| 内容 | 交接到什么程度 |
|---|---|
| 实现落点 | 已有／拟新增模块、文件、职责、改动种类及依赖顺序；文件树注明基线和拟议／实际；依赖与包布局见下 |
| 接口与数据 | 签名、类型、字段、单位、可空性、约束、返回值、副作用和错误；引用公共契约，不另取同义名称 |
| 执行逻辑 | 入口、调用、分支、算法和事务边界；伪代码保留异常、退出与清理，省略范围可辨认 |
| 状态与失败 | 状态、触发、守卫、动作、不变量与可见结果；按需覆盖幂等、并发、超时、取消、重试停止和资源释放 |
| 兼容与实施 | 新旧接口映射、实施依赖、迁移／回退条件；变更架构决定时明确提出待决 |
| 代码规范 | 按代码规范指导交接本次规则；重点注释写明位置、解释内容与核验方式，无代码示例也须交接；小任务用条目 |
| 验证 | 需求／风险对应输入、前置状态、操作、预期、判定依据及测试接入点；按共用测试指导区分计划、用例、实现和实测 |

能用签名、类型或短步骤说清的内容不再画图；复杂交互按 5.8 表达。设计调用链是预期路径，实际调用栈须有运行记录。拟议代码保持选定命名、类型与注释规则，不搬入与决策无关的完整实现。

### 依赖表与包布局

程序详细设计交代当前方案的依赖与代码落点，沿项目现状，不为形式另建通用层。

**依赖表**：只列实现本方案或理解边界所需的依赖，含未变而关键的既有依赖；覆盖内部模块、第三方库、必要标准库、外部服务或平台契约，不转储锁文件或全部传递依赖。字段：依赖项及类别（内部／第三方／标准库／外部服务，构建与测试专用另标）；用途（完整选型论证回原章节）；版本或契约约束（声明范围不冒充已锁定值，内部包不编独立版本号）；使用方 → 提供方（箭头表依赖，不表数据流或实施先后）；变更状态（既有沿用／拟新增／升级／替换／移除／候选待决，拟新增不写成已引入）；依据（清单、导入代码、契约或已确认决策，拿不到就标待核实）。许可、安全与失败处理仅在影响选型或行为时展开。无新增第三方依赖须写明，不写成无任何依赖。

**包布局**：以目标模块及直接依赖为范围，先看现状再写目标，语言、构建与命名沿用项目。只展示相关主干或受影响子树，保留包／模块边界、公开入口、关键实现与测试落点；区分既有／新增／修改／移动／删除或拟定，移动给旧 → 新路径；讲清对外入口、内部实现与允许的依赖方向，不凭空要求统一层次架构。树、依赖表、接口与测试用同一套名称，树上已写清的职责不复制成重复表。包树回答放在哪里，不替代结构关系图。

局部小改动、纯架构设计或轻量文类不硬塞完整依赖表与项目树；依赖与布局不变且不影响理解时，一段说明加相关路径及现状引用即可，关键既有关系影响理解仍需写。

## 分支检查

- 契约：输入输出、约束、副作用与错误能供调用方使用；字段与上层约定一致。
- 行为：正常、边界与适用失败路径连贯；状态及不变量、事务／异步边界、取消与清理可定位。
- 落点：关键需求对应模块与文件；未知内容标为拟定，实施顺序无缺失依赖。
- 依赖与布局：依赖类别、契约状态与使用方向清楚，布局标记与公开入口一致；树不冒充结构图，轻量任务未被强加完整表与树。
- 代码约束：有取样依据或新项目草案；风格、命名、类型一致，重点注释已交接且可核验，不留待施工自行决定；公共兼容和范围外代码保留。
- 验证：成功条件可观察，判定有依据；缺证据不记通过，关键风险与验证缺口未被遗漏。
- 复杂度与未决：落实父模板 D1 和观测要求，不添加无需求支撑的组件；关键待决及其影响清楚。
