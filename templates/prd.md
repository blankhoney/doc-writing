# PRD（产品需求文档）

> 定义一个功能"为什么做、做成什么样、怎么验收"，让工程团队能直接排期实施。

> **示例使用范围**：本模板通过变体结构、锚定节、模块与类型验证标准使用，不附样本正文。见[来源说明](../examples/SOURCES.md)。

## 变体选择

```
任务的范围和风险？
  ├─ 单点改动，≤1 周           → Brief
  ├─ 单团队功能，2-6 周        → Lean（默认）
  ├─ 跨团队或战略级功能         → 完整
  └─ 需求条目库（持续维护）     → 需求条目库
```

---

## 变体 A: Brief

> 一页纸可完成的小功能——问题清楚、方案确定、不需要跨团队对齐。

### 锚定节

| 锚定节 | 锚问 | 排版 |
| -------- | ------ | ------ |
| 问题 | 谁受影响？影响程度及依据？ | 倒金字塔 |
| 目标与非目标 | 成功的衡量标准？不做什么？ | 倒金字塔 |
| 验收标准 | 怎么判断做完了？ | 契约表 |

### 可插模块

无。Brief 变体不插入模块——需要插入模块说明复杂度已超出 Brief 范围，升级为 Lean。

---

## 变体 B: Lean（默认）

> 单团队可交付的功能——需要明确用户画像、可验证的成功条件、列出验收条件。

### 锚定节

| 锚定节 | 锚问 | 排版 |
| -------- | ------ | ------ |
| 问题 | 谁受影响？影响程度及依据？现状为什么不行？ | 倒金字塔 |
| 目标与非目标 | 成功条件是什么？数量型目标用什么指标？明确不做什么？ | 倒金字塔 |
| 目标用户 | 谁是第一批用户？用户当前怎么解决这个问题？ | 倒金字塔 |
| 验收标准 | 功能上线的判定条件（可测试的契约） | 契约表 |

### 可插模块

| 模块名 | 锚问 | 排版 | 格式规范 | 有效性检验 |
| -------- | ------ | ------ | --------- | ----------- |
| 竞品分析 | 竞品怎么解决这个问题？我们的差异化在哪？ | 比较表 | 竞品名 / 方案 / 优势 / 劣势 / 我们的差异；只列与当前需求有关的实际比较对象，不设数量下限 | 比较有来源且有助于理解产品选择；不要求竞品必须有更优维度。纯为凑数或与需求无关时删除 |
| 技术约束 | 技术限制会如何影响产品方案？ | 定义列表 | 约束项 / 影响 / 应对方式 | 每条约束必须影响产品方案的某个决策；与产品无关的纯技术细节不放这里 |
| 用户故事 | 用户完成核心任务的具体路径？ | 有序步骤 | "作为 [角色]，我想 [动作]，以便 [价值]"格式，每条附验收条件 | 每条用户故事可独立验收；无法写出验收条件的故事说明需求不明确 |
| 成功指标 | 上线后用什么数据衡量成功？ | 契约表 | 指标名 / 目标值 / 测量方式 / 观测周期 / 基线（需比较变化时） | 数量型目标有目标值和测量方式，需要比较变化时给出基线；缺数据时说明待验证内容与获取方式。非数量型目标用可验证的验收条件，不另造数字 |

## 变体 C: 完整

> 跨团队或战略级功能——需要多方对齐，增加竞品分析、里程碑、风险评估。

### 锚定节

| 锚定节 | 锚问 | 排版 |
| -------- | ------ | ------ |
| 问题 | 谁受影响？影响程度及依据？当前方案为什么失败？ | 倒金字塔 |
| 目标与非目标 | 可验证的成功条件 + 明确排除项 | 倒金字塔 |
| 目标用户与场景 | 用户画像 + 核心场景 + 当前 workaround | 倒金字塔 |
| 功能设计 | 核心交互和信息架构 | 问题→方案→代价 |
| 验收标准 | 全量验收条件 | 契约表 |
| 里程碑 | 各阶段交付物和日期 | 时间线 |

### 可插模块

继承 Lean 变体所有模块，额外增加：

| 模块名 | 锚问 | 排版 | 格式规范 | 有效性检验 |
| -------- | ------ | ------ | --------- | ----------- |
| 竞品分析 | （同 Lean） | 比较表 | （同 Lean） | （同 Lean） |
| 风险评估 | 哪些因素可能导致项目失败或延期？ | 契约表 | 风险 / 概率（高/中/低） / 影响 / 缓解措施 / 负责人 | 每条风险有具体缓解措施和负责人；"可能有技术风险"不算 |
| 依赖清单 | 交付依赖哪些外部团队或系统？ | 契约表 | 依赖项 / 提供方 / 需要日期 / 当前状态 / 兜底方案 | 每项依赖有明确的需要日期和兜底方案 |
| 数据与隐私 | 涉及哪些用户数据？合规要求？ | 定义列表 | 数据类型 / 存储位置 / 保留期限 / 合规依据 | 涉及用户数据时必须填写；不涉及则删除此模块 |

## 变体 D: 需求条目库

> 持续维护的需求集合——用于大型产品线的需求跟踪和版本规划。

### 锚定节

| 锚定节 | 锚问 | 排版 |
| -------- | ------ | ------ |
| 产品愿景 | 这个产品解决什么根本问题？ | 倒金字塔 |
| 需求索引 | 当前所有需求的分类和状态 | 索引 + 深链 |
| 版本规划 | 哪些需求进哪个版本？ | 时间线 |

### 可插模块

| 模块名 | 锚问 | 排版 | 格式规范 | 有效性检验 |
| -------- | ------ | ------ | --------- | ----------- |
| 需求条目 | 单条需求的完整描述 | 定义列表 | ID / 标题 / 问题 / 验收标准 / 优先级 / 状态 | 每条有验收标准和优先级排序依据 |
| 版本主题 | 这个版本的主线是什么？ | 倒金字塔 | 版本号 / 主题一句话 / 包含需求 ID 列表 | 版本有明确主题，不是"杂项合集" |

## 类型验证标准（Phase 4 Step 1c）

PRD 通过通用收尾检查（3.5）后，额外检查以下专用项：

| 检查项 | 验证方法 | 不通过时处理 |
| -------- | --------- | ------------ |
| 成功条件可验证 | 每个目标是否有可观测的成功条件？数量型目标是否给出目标值和测量方式，需要比较变化时是否有基线？ | 补充判定条件；仅对必要的数据缺口说明待验证内容与获取方式，不为非数量型目标另造指标 |
| 非目标存在 | 是否明确列出了"不做什么"？ | 至少列出 1 条非目标 |
| 验收可测试 | 每条验收标准是否可以写成测试用例（输入→预期输出）？ | 重写为可测试格式 |
| 用户具体 | "目标用户"是否有具体画像或数据，而非"所有用户"？ | 补充用户特征和数据 |
| 问题有依据 | "问题"部分是否有支撑影响程度的数据或具体事实（工单、观察记录、已确认约束）？ | 补充依据；必要证据缺失时说明缺口与验证方式，不为形式量化而补造数字 |
