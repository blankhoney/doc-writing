# 技术设计文档

> 记录一个技术决策的问题、方案、代价和未决项，让团队理解"为什么这么做"并能直接实施。

> **示例使用范围**：备忘与 Lean 保留本仓库源码改编，示范深度差异，不是历史决策或本次实测。见[来源说明](../examples/SOURCES.md)。

## 变体选择

本模板用于技术方案与决策；介绍现有项目的组成和设计理由时按 Explanation 组织，不因标题含架构或读者负责验收就写成本轮变更。涉及组成、职责、边界与依赖时按 5.8.2 使用 Mermaid 结构关系图；一句话可说清的简单关系除外。

先选任务分支，完整读取对应指导及检查清单，再按范围选下方变体；综合任务读两份，不复制八套模板：

| 任务 | 指导 | 在变体内展开 |
|---|---|---|
| 系统边界、职责、交互与取舍 | [架构方案](tech-design/architecture.md) | 方案／方案设计 |
| 文件落点、接口数据、算法状态与错误 | [程序详细设计](tech-design/implementation.md) | 方案／方案设计；代价与未决仍归原节 |

接续 PRD、初版方案与所选代码版本，把关键需求对应到对象、行为、失败路径和验证。主动补适用缺口；模板空项不自动变成需求或新组件。范围、安全、兼容、高成本或不可逆变化给推荐方案与待确认点，新建议不写成已批准／已实现。

实际提出技术架构决策前，完整读取[架构文档质量规范 D1](../docs/modules/constraints-architecture.md)，包含详细设计中真实涉及的架构选择，不是验证阶段才读；以下 D1 清单为本类型层视图，适用与豁免不变，选中模板后仍完整读取。

新建／行为变更设计主动读[测试证据指导](../docs/modules/test-evidence-presentation.md) §5，再按该文件入口读相关完整节；用户无需先讨论测试。小任务在原节简写验证，复杂安排用[测试报告](test-report.md)的测试计划 C。备忘不插模块；无代码的新项目可直接详细设计，不强制先出架构文档。

先给直接实现，新增复杂度按 D1 核对。复用已有记录简述计划、实际动作与关键选择，不复制全量轨迹。仅设计 Agent 工具时检查 ACI：名称、类型、参数、前置条件与返回是否直观，按需校验和确认高影响操作。

```
任务的范围和风险？
  ├─ 小改动，≤1 周，方案确定    → 备忘
  ├─ 单团队功能，有取舍          → Lean / Google 式（默认）
  ├─ 跨团队或有架构影响          → 内部 RFC
  └─ 外部交付 / 合规要求         → SDD（仅此时）
```

## 变体 A: 备忘

> 一页纸的技术决策——问题清楚，方案明确，风险可控。

### 锚定节

| 锚定节 | 锚问 | 排版 |
|--------|------|------|
| 问题 | 为什么要改？现状有什么具体问题？ | 倒金字塔 |
| 方案 | 具体改什么？关键变更列表 | 问题→方案→代价 |
| 代价 | 这个方案的已知代价和约束？ | 问题→方案→代价 |
| 未决 | 还有什么没确定？ | 倒金字塔 |

### 可插模块

无。备忘变体不插入模块。需要备选方案或迁移计划说明复杂度超出备忘范围，升级为 Lean。

### 示例

> 来源：[doc-lint.py](../runtime/doc-lint.py)（本包当前源码，`blank`、`mask_markdown`、`scan_text`）。短篇只说明保留行号的选择；未运行或测量。

```markdown
# 候选扫描保留物理行号

## 问题
候选需要定位到原文行号；直接删除代码行会使后续行号偏移。

## 方案
将排除区域的非换行字符替换为空格，扫描剩余文字。
输出候选时使用原文物理行号，不使用删除后的行号。

## 代价
原文与掩蔽文本同时保留，占用额外内存；开销未测量。

## 未决
本例未评估大文件的内存峰值。
```

## 变体 B: Lean / Google 式（默认）

> 单团队的技术设计——有明确取舍，需要记录决策理由，团队需要对齐。对应 Google Design Docs 推荐的 10-20 页格式中的精简版。

### 锚定节

| 锚定节 | 锚问 | 排版 |
|--------|------|------|
| 目标与非目标 | 这个设计要实现什么？明确不解决什么？ | 倒金字塔 |
| 背景 | 客观现状——当前系统状态、问题数据、约束条件 | 倒金字塔 |
| 方案 | 具体设计是什么？关键组件和交互？ | 问题→方案→代价 |
| 代价与取舍 | 方案牺牲了什么？已知限制？ | 问题→方案→代价 |
| 未决项 | 哪些问题待定？决策条件是什么？ | 定义列表 |

### 可插模块

| 模块名 | 锚问 | 排版 | 格式规范 | 有效性检验 |
|--------|------|------|---------|-----------|
| 备选方案 | 考虑过哪些替代方案？为什么没选？ | 比较表 | 方案名 / 优势 / 劣势 / 放弃原因；只列现实候选，无候选时不凑数 | 候选真实且有淘汰依据即可保留，不要求至少一个维度更优；纯为凑数或与决策无关时删除 |
| 性能评估 | 方案的性能预期和验证计划？ | 契约表 | 指标 / 当前值 / 目标值 / 测量方式 | 有基准数字或估算依据；"性能良好"无数据 → 删除 |
| 迁移计划 | 现有系统怎么过渡到新方案？ | 有序步骤 + 验证信号 | 步骤 / 验证信号 / 回滚方案 | 有具体步骤和回滚方案；"逐步迁移"无细节 → 删除 |
| 安全分析 | 方案引入了什么安全风险？如何缓解？ | 定义列表 | 威胁 / 影响 / 缓解机制 | 安全变更必须填写；无安全影响 → 删除此模块 |
| 可观测性 | 需要判断什么，已有信号是否足够？ | 信息获取表 | 问题 / 现有事实源或采集点 / 必要字段与单位 / 使用及缺失处理 | 生产变更说明已有信号与必要缺口，不强制新指标、告警或仪表盘；普通遥测失败独立记录，保留确证业务事实；明确的审计／安全前置照常执行 |
| 验证设计 | 如何判定关键要求与失败风险？ | 场景表或条目 | 输入与前置 / 操作 / 预期与判定依据 / 数据环境与证据安排 | 新建或行为变更设计主动补齐；小任务在原节简写，复杂安排按测试计划 C |

### 示例

> 同题长设计片段，仅含方案与取舍，省略目标、背景和未决项。来源同上，按源码解释当前实现，未运行或测量。

```markdown
# 候选扫描保留物理行号（长设计节选）

## 方案

### 职责
| 函数 | 输入 → 输出 | 职责 |
|------|------------|------|
| `blank` | 文本 → 等长掩蔽文本 | 非换行字符替换为空格 |
| `mask_markdown` | 原文行列表 → 掩蔽行列表、范围提醒 | 识别有限 Markdown 排除区域 |
| `scan_text` | 文本、词表、跳过的格式类别 → 记录、抑制数 | 按物理行扫描候选并处理抑制 |
| `main` | 文件参数 → 终端报告、退出码 | 读取词源和文件，汇总扫描记录 |

### 处理流程
1. `scan_text` 去掉开头 BOM，将 CRLF 转成 LF，再分成物理行。
   文件末尾换行不额外计为一行。
2. `mask_markdown` 掩蔽首行元数据、围栏、反引号代码及有限链接目标等区域。
   掩蔽不删除换行，返回的行与原文逐行对应。
3. `scan_text` 同时遍历原文行和掩蔽行，在掩蔽行上匹配候选。
   格式候选按匹配偏移截取原文，保留代码片段等上下文。
4. 有效抑制注释只作用于下一物理行。记录按行号排序，交给 `main` 输出。

### 输出边界
候选记录含物理行号、类别与命中文本；范围提醒与候选分开计数。
围栏未闭合时会排除后续文本并报告范围提醒。

## 代价与取舍
保留等长掩蔽文本，使匹配位置可以直接对应原文，不必另建删除后的行号映射。
代价是原文、掩蔽文本及处理中间字符串同时占用内存；峰值未测量。

当前实现只识别有限 Markdown 边界，不引入完整解析器。
缩进代码、HTML 和深层嵌套链接不解析。
```

## 变体 C: 内部 RFC

> 跨团队的重大技术决策——需要广泛评审，影响架构方向，可能不可逆。锚定节要求覆盖 D1 架构文档质量清单。

### 锚定节

| 锚定节 | 锚问 | 排版 |
|--------|------|------|
| 摘要 | 一段话说清楚决定了什么（读完即可决定是否继续读） | 倒金字塔 |
| 目标与非目标 | 可验证的成功条件 + 明确排除项 | 倒金字塔 |
| 背景与约束 | 当前系统状态、驱动因素、关键约束条件 | 倒金字塔 |
| 方案设计 | 架构、组件、接口、数据流 | 问题→方案→代价 |
| 备选方案 | 考虑过的替代方案及取舍分析 | 比较表 |
| 代价与风险 | 已知代价、风险及缓解措施 | 契约表 |
| 未解决问题 | 待定事项、决策条件、时间节点 | 定义列表 |

### 可插模块

继承 Lean 变体所有模块，额外增加：

| 模块名 | 锚问 | 排版 | 格式规范 | 有效性检验 |
|--------|------|------|---------|-----------|
| 系统边界 | 各组件/团队的职责边界？ | Mermaid 图 + 定义列表 | 组件名 / 职责 / 不负责什么 | 每个组件职责不重叠；出现 God Component 信号 → 重新拆分 |
| 故障设计 | 系统怎么失败？怎么降级和恢复？ | 契约表 | 故障场景 / 影响范围 / 降级行为 / 恢复步骤 / 恢复时间预期 | 不能只有 Happy Path；至少覆盖单点故障、级联故障、外部依赖失败 |
| 一致性选择 | 哪些操作强一致？哪些最终一致？ | 比较表 | 操作 / 一致性级别 / 原因 / 不一致时的影响 | 涉及分布式状态时必须填写 |
| 决策可逆性 | 哪些决策可逆？高成本或不可逆决策的依据？ | 比较表 | 决策 / 可逆性 / 实施及回退成本 / 依据充分性 | 高成本或不可逆决策需更充分论证 |
| 里程碑 | 交付计划和阶段划分？ | 时间线 | 阶段 / 交付物 / 日期 / 验证标准 | 每个阶段有可交付的产出物和日期 |

## 变体 D: SDD（Software Design Description）

> 面向外部客户或合规场景的正式设计文档。仅当客户合同或法规明确要求时使用。

### 锚定节

继承内部 RFC 所有锚定节，额外增加：

| 锚定节 | 锚问 | 排版 |
|--------|------|------|
| 文档元数据 | 版本、作者、审批链、变更历史 | 定义列表 |
| 术语表 | 全文关键术语的统一定义 | 定义列表 |
| 合规映射 | 满足哪些合规要求？ | 契约表 |

### 可插模块

继承内部 RFC 所有模块。SDD 的模块通常全部启用。

### 示例

> SDD 格式因合同/法规而异，不提供通用示例。参考 IEEE 1016 获取正式结构。

## D1 架构文档质量清单

内部 RFC 和 SDD 变体的方案设计必须覆盖以下检查项（来源：约束体系 §3.4 D1）。Lean 变体覆盖与当前设计直接相关的条目——若设计不涉及分布式状态，跳过"一致性选择"；若不涉及已有系统，跳过"迁移方案"。

### 必须回答的问题

| 领域 | 必须说明 |
|------|---------|
| 决策范围 | 本文决定什么、不决定什么、为什么现在必须决策 |
| 约束条件 | 成本、性能、安全、合规、团队能力、交付周期、历史系统 |
| 系统边界 | 哪些能力属于平台、业务、模型、基础设施、外部系统 |
| 组件职责 | 核心组件各自负责什么，不出现职责高度重叠 |
| 数据与状态 | 关键数据、状态、控制权分别由谁持有 |
| 调用关系 | 核心调用链、数据流、控制流；哪些同步、哪些异步及原因 |
| 故障设计 | 关键故障场景，系统如何失败、降级和恢复 |
| 一致性选择 | 哪些必须强一致，哪些允许最终一致 |
| 安全机制 | 安全、权限、数据隔离的具体架构机制 |
| 决策可逆性 | 哪些可逆、哪些不可逆；高成本或不可逆需更充分依据 |
| 复杂度意识 | 对应哪条需求、现有机制能否替代、删除影响、组合失败点与维护成本；优先直接流程及删减合并 |
| 迁移方案 | 现有系统的迁移方式、兼容关系、切换边界 |
| 未解决问题 | 明确列出尚未解决的问题 |

### 常见方案论证要求

| 方案 | 必须说明 |
|------|---------|
| 加缓存 | 缓存失效策略、一致性代价、冷启动方案 |
| 加重试 | 幂等性保证、重试风暴防护、超时上限 |
| 加消息队列 | 消息顺序性要求、消费失败处理、积压监控 |
| 加服务/中间层 | 新增运维成本、团队维护能力 |
| 加人工审核 | 审核延迟影响、审核标准是否可量化 |

### 架构反模式

| 反模式 | 识别信号 |
|--------|---------|
| God Component | 一个组件同时承担编排、决策、存储、治理、权限等大量职责 |
| 伪复杂度 | 组件数量增加但职责没有增加 |
| Happy Path Only | 只描述正常路径，不说明失败时发生什么 |
| 安全关键词堆砌 | 安全章节只出现关键词，没有具体边界和机制 |
| 抽象组件命名 | "智能决策中心""统一能力平台"等名称，解释不清具体职责 |
| 无条件套用模板 | 不考虑当前约束，直接套标准架构模板 |

## 类型验证标准（Phase 4 Step 1c）

技术设计文档通过通用收尾检查（3.5）后，额外检查以下专用项：

| 检查项 | 验证方法 | 不通过时处理 |
|--------|---------|------------|
| D1 必答问题覆盖 | 逐条检查 D1 清单中与当前设计范围相关的问题是否回答 | 补充回答或说明待验证内容与验证方式 |
| 取舍排除性检验 | 每个"建议/选择"替换为反面后，论据是否需要重写？（G3） | 论据不变 → 重写论据 |
| 组件命名与关系 | 名称是否对应具体职责？架构结构图是否按 5.8.2 回答本节组成、边界与依赖，并实际渲染核对？ | 修正名称和关系，不以目录树或步骤图替代；一句可说清的简单关系无需图，未能渲染则说明未验证 |
| 备选方案非凑数 | 每个备选是否为现实候选，并有淘汰依据？ | 保留真实候选及其依据；缺依据时说明缺口与核实方式，只删除凑数或与决策无关的候选 |
| 目标可验证 | 每个目标是否有可观测的成功条件？ | 补充量化指标或判定条件 |
| 非目标明确 | 是否列出了不解决什么？ | 至少列出 1 条非目标 |
| 代价有数字 | 每个代价/风险是否有具体影响评估（时间/成本/性能）？ | 补充度量或说明估算依据 |
| 分支可交接 | 所选分支完整检查是否执行，需求、契约、行为、代码约束与落点是否对应？ | 按分支补适用缺口；新建议与已确认项分清 |
| 验证有判据 | 新建／变更设计是否主动给出可观察预期与判定依据，适用测试指导是否读到？ | 补验证设计；缺有效性材料说明限制，不预填成功 |
