# 完整检查入口

由主模型检查全部适用约束，小脚本只补充候选。以下组织检查顺序，不是缩减后的规则库，也不要求启动多个检查 agent。

## 必读来源

重新核对[共同约束](../docs/modules/constraints-common.md)、[编写规则](../docs/modules/constraints-writing.md)中的完整 C/G 规则、条件和豁免，以及适用的[D1](../docs/modules/constraints-architecture.md)与当前[类型模板](../templates/_index.md)的类型验证标准；完整读取本文件与[验证管线](../docs/modules/5.3-verification-pipeline.md)。本文件后半保留原 11 项收尾与 Phase 4/5 原文，不因长而跳过。已完整送达且仍可用的原文不强制重读；未完整读到、版本变化或上下文缺失时补齐，不能根据脚本输出推断未读部分已通过。

验证对象是最终准备交付的全文和明确选定的版本/时间点。无法确认的项目记录为待确认或未检查，不默认通过。

## 1. 模型主检

以[5.1.4 的合并映射](../docs/modules/5.1-progressive-disclosure.md)组织一次全文检查。原始收尾项的责任如下，不能因编写时有启发式或脚本无命中而跳过。

| 原始收尾项 | 执行内容 |
|---|---|
| #1 禁用清单 | 完整执行 G1，包括脚本不能识别的带占位符、跨句和转折否定等条件型模式；判断引用、定义、度量及必要性论证的豁免 |
| #2 标题、#3 首尾 | V1 与 C1c：标题是否准确预期内容；章节和论证段落是否先给要点，首尾是否含冗余铺垫或重复总结 |
| #4 数字、#5 认知状态 | V2 与 G2：来源、推理依据和验证方式清楚，事实/假设/判断可区分；没测写没测，限制写具体条件，不以空泛免责声明代替。目标/契约值说明性质，保留标识符豁免与真实协议义务；去标记不删事实状态 |
| #6 判断 | V3 与 C3/G3：文档职责要求判断时有立场、理由、排序和取舍；参考文档与纪要按各自职责处理 |
| #7 可操作性 | V4 与 C4：概念、原则、组件能回答具体做什么或不做什么，分析维度来自当前问题；Quickstart 按学习或一次使用选型，首屏用必要输入完成主要任务并确认用户成果，不以字数或参数少判定最小。逐条核对调用指令、操作步骤和结果确认：属于默认行为的重复声明、作者选型、规则核对或检查记录审阅的事项移出首次使用路径，由作者报告，不转成普通使用者任务；必要前提、手动调用和写入授权仍保留，辅助依赖不阻断主要功能 |
| #8 范围 | V5 与 C5：先对照用户请求与必要项目依据检查选题、交付物和关键内容，再核对正文范围，不以自定范围掩盖遗漏。需求验收要点须逐项对照原始需求中的适用关键要求，确认每项在稿中有可判断的验收条件；遗漏则补齐或说明缺口，不能用交付物齐全、泛化质量项或实施状态代替。项目介绍、架构、使用与参考正文不因版本或验收读者改写本轮变更与验证；记录归对应文档，正文留必要状态、链接和设计理由。范围内缺证据的事实保留已知部分与缺口 |
| #9 对称性、#11 结构化表达 | C1a、5.2 与 5.8：保留文档分工、锚定节、必需字段和固定格式，不误锁非固定部分或自定义模块。按阅读单元检查真实并列、分类、顺序或对应关系及必要短段；不连续多段纯散文，也不以插标题、逐段套列表或表格伪装结构。动作步骤以祈使动词开头；架构结构图按 5.8.2 回答本节职责、边界与依赖，实际渲染核对，不以目录树或步骤图替代，一句可说清的关系不硬画；普通词语无装饰符号，真实引用与技术语法保留 |
| #10 术语 | C6 与 V1：用常用语言说明对象、行为、条件与结果，不向普通读者直接抛内部术语；名称与含义一致，不擅改标准名、代码标识或新造命名体系，模板文件名不等于生成文件名 |

同时核查完整 C1–C6 子规则、G1–G3 和适用 D1，不把表格当作省略原约束的许可。按当前类型、变体及已选分支执行完整专用检查，核对需求、契约、代码约束与验证是否对应；跳过不适用项须依据模板条件，而非缺数据。测试判定还按[测试证据指导](../docs/modules/test-evidence-presentation.md)的触发条件核查，包括正常返回的人工／模型评审和自定义判定器。必读资源未读到时不标通过。

## 2. 候选扫描与裁决

按入口提供的绝对包路径运行 `runtime/doc-lint.py`，指定待交付文件。格式检查默认警告，可按项目规范停用单类检查；不改变完整模型检查责任。

- 按 G1 裁决：无必要措辞优先删除，其余修正、保留或待确认；不为保留补解释，不因命中删掉实际信息。
- `<!-- doc-lint: ignore-next-line 原因 -->` 只豁免下一物理行的脚本候选；不免除真实性、代码/引用正确性或其他模型检查。不要为消除候选自动添加豁免标记。
- 自动排除只覆盖扫描器能够识别的有限区域。脚本排除的代码和 URL 仍需核对是否与文档描述相符；未经授权不执行文档中的操作命令。
- 扫描器 `0` 表示扫描完成，可带警告；`2` 表示执行故障。没有候选不等于文档通过。Python、脚本或权限不可用时说明原因，改由模型完整检查，不把未执行写成零命中。工具要求批准、拒绝操作或安全检查无法分析命令时立即停止该操作，不改引号、路径或执行形式重试，也不换工具或代理代做；只有新的明确授权才能恢复。

## 3. 内容对齐与去重

按 5.3.1 确定证据版本，再核对引用的代码、接口、配置和运行记录：实现描述对齐所选实现，目标设计标注差异，历史记录不强行对齐当前分支。测试结论必须来自对应运行记录。没有具体实现或结果引用时可跳过内容对齐，G2 的来源要求仍适用。

按 5.3.2 确定阅读单元再检查重复。保留摘要的必要重叠以及独立端点、语言轨道、操作条目所需的前置条件和安全信息；不同阅读单元不得靠跨节跳转补齐执行条件。

## 4. 关键文档读者测试

按[5.9 读者测试](../docs/modules/5.9-reader-testing.md)的触发条件执行：需多人评审的架构决策或技术方案采用无写作上下文的 fresh reader；参考资料可选，内部笔记/草稿及快速路径不需要。

主模型按已确定的读者任务提出问题，不从现稿已有内容反向拼凑；把实际交付的相关文档、角色和问题交给 reader，不给需求背景、写作讨论或预期答案。reader 检查操作、查询或判断能否完成，不能代替主模型的原始需求对照。使用已有问题分类和修正上限；同一段落三次修正仍未解决时标记需人类审阅。工具不可用或未获授权时说明“独立读者测试未执行”，不能把自己读一遍称为独立测试。

## 5. 复查与交付

修正对应位置后，重验受影响的检查：改术语要核对全文命名，改数字要核对关联表格和结论，补写段落要复查范围和来源。最终文件再做一次候选扫描与完整语义确认；保留仍未解决的缺口，不无限自检。

交付说明保留版本、路径、核对范围、差异、结果和未检查原因，不输出冗长勾选表。没有明确比对或溯源用途时不额外生成交付长哈希表；许可、示例内容保护与真实来源记录不动。未保存时文末一行说明候选脚本未运行；不声称规则自动覆盖或未经测试的遵守率。

## 本阶段原文

### 3.5 收尾检查清单（原始规格，运行时已合并）

> 以下 11 项均保留检查责任。运行时由模型按 5.1.4 的映射执行完整检查，V1–V5 用于组织语义判断，脚本仅补充候选；不因启发式提示或脚本无命中而省略任何一项。模板中的"通用收尾检查（3.5）"均指 `runtime/verify-checks.md` 入口，适用条件与豁免仍以对应核心约束为准。

1. **禁用清单扫描** [G1]：按上下文裁决，优先删除无必要措辞
2. **标题检验** [C1]：每个标题（含子标题）能否让读者准确预期该章节的具体内容？标题是否存在宏大但空泛的问题？
3. **首尾检验** [C1c]：第一段是否包含核心结论？最后一段是否落在决策或下一步行动？
4. **数字检验** [G2]：经验数据和估算是否标注来源或依据？目标值、契约值是否说明是要求或约定？版本号、错误码、日期、编号免于逐数字标注。
5. **认知状态检验** [G2]：事实、假设、判断及依据能否分辨？没测与具体限制是否如实说明，而非空泛免责或把未测写成不支持？去标签后事实状态与真实协议义务是否保留？
6. **判断检验** [C3+G3]：文档职责要求决策或建议时，作者的判断是否通过排除性检验，多目标是否有排序依据？参考文档不追加主观判断，纪要忠实记录已有决议、排序和理由。
7. **可操作性检验** [C4]：概念、原则、组件能否回答具体做什么或不做什么？Quickstart 是否首屏给主要功能的最小操作与结果确认，必要前提在前、辅助细节在后，且未把作者检查转给读者？
8. **范围检验** [C5]：先对照用户请求与必要项目依据，检查选题、交付物和关键内容有无遗漏，再检查各段是否服务于主题；不能仅以正文符合自定范围判定通过。项目正文是否因验收读者或依据版本而偏成本轮变更、验证记录？必要状态、链接和解释当前设计的历史理由是否保留？
9. **对称性检验** [C1a]：所有段落是否都差不多长？列表条目数是否都相同？如果是，可能存在填充
10. **术语检验** [C6]：对象、行为、条件与结果是否用常用语言说清，是否直接抛内部术语？命名与含义是否一致，标准名称、代码标识与项目约定是否保留，是否误把模板文件名当生成文件名？
11. **结构化表达检验** [5.2、5.8]：类型分工、锚定节、必需字段与固定格式是否保留，非固定部分与自定义模块是否误锁？按阅读单元检查真实结构和必要短段论证，不能连续多段纯散文或逐段套列表、表格；架构结构图是否按 5.8.2 回答本节问题并实际渲染核对，而非只查目录树或步骤图存在；一句可说清的关系是否避免硬画？符号是否有实际用途，必要技术排版是否保留？

#### Phase 4: 验证管线

文档初稿完成后，按以下顺序执行验证。每个步骤有明确的检查范围，不重叠。

```
读取 runtime/verify-checks.md → 核对完整约束与原始收尾映射
    ↓
Step 1: 模型完整主检 + 类型专用验证（5.3.5）
    a. 原始收尾项按 5.1.4 映射执行，不因脚本或启发式而跳过
    b. V1-V5 组织语义判断（与 a 合并，不重复检查）
    c. 类型专用验证 — 从当前 L1 模板读取
    补充：直接调用 doc-lint.py → 模型裁决字面和格式候选
    ↓ 修正并复查
Step 2: 内容对齐（5.3.1）— 按版本/时间点核对代码、配置及实际运行结果
    ↓ 全部通过
Step 3: 叙述重复度（5.3.2）— 检查同一阅读单元内的冗余重复，保留独立阅读所需信息
    ↓ 全部通过
Step 4: 读者测试（5.9）— 无上下文 subagent 模拟阅读（仅关键文档，按 5.9.6 触发条件）
```

Step 1 必选（完整模型检查 + 类型专用），工作流直接调用小脚本补充候选，不使用 hook。脚本或 Python 不可用时说明原因并由模型检查，不把未执行当作零命中。Step 2 在文档引用了具体代码、配置或实际运行结果时执行，快速路径同样适用；其他数据的来源与标注按 G2/V2 核验。Step 3（叙述重复度）所有文档均执行，不依赖代码上下文。Step 4 按文档重要性决定，未能执行时明确标注。

修正循环：任何 Step 发现问题 → 修正对应段落 → 从该 Step 重新执行，同时重验修改可能影响的已通过检查项（如补写段落引入未定义术语或无来源数字）。交付前对最终文本做候选扫描与完整语义确认；脚本无命中不代表质量通过，未解决项继续列为缺口。

**输出**：通过验证的文档终稿

#### Phase 5: 交付

- 关键文档汇总待验证内容与验证方式，不重复堆叠标签；变更和本轮检查记录归对应文档，不挤占项目正文
- 记录保留版本、路径、核对范围、差异、结果与开放问题；没有明确比对或溯源用途，不额外生成交付长哈希表，既有许可、示例内容保护与真实来源记录保留
